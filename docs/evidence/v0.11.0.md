# v0.11.0 external SARIF correlation record

Status: unreleased product/schema candidate, locally validated on 2026-09-02. This record does not claim that a tag or release exists.

## Question

Can one external SARIF 2.1.0 result for a deliberately vulnerable MCP server be attached to an already observed runtime component only when stable artifact identity and SHA-256 agree, trigger policy and CycloneDX VDR output, and retain no source/finding content beyond an explicit metadata allowlist?

## Standards and tool boundary

The importer targets the [OASIS SARIF 2.1.0 specification incorporating Errata 01](https://docs.oasis-open.org/sarif/sarif/v2.1.0/sarif-v2.1.0.html). The executable check downloads its official OASIS schema and accepts it only at SHA-256 `c3b4bb2d6093897483348925aaa73af03b3e3f4bd4ca38cef26dcb4212a2682e`.

The real scanner fixture uses [gosec v2.28.0](https://github.com/securego/gosec/releases/tag/v2.28.0), which emits SARIF directly. gosec is a test producer, not a runtime dependency, built-in scanning engine, endorsed verdict source, or format-specific branch in the importer. The same core contract can accept another producer only if its binding-critical SARIF fields obey the standard subset described in [`docs/SCHEMA.md`](../SCHEMA.md).

SARIF `level` values are reporting levels: `none`, `note`, `warning`, and `error`. They are not CVSS/CycloneDX severities. v0.11 therefore retains the standard value for policy but does not translate `error` into `high` or `critical`.

## Identity contract

The MCP runtime adapter supplies two project-owned attributes:

- `aiebom.artifact.uri=scripts/live/mcp_runtime/main.go`;
- `aiebom.artifact.sha256=<current file digest>`.

Normalization retains the URI and makes the digest the MCP server's selected `digests.sha256` value. At SARIF import time, `--artifact scripts/live/mcp_runtime/main.go` reopens the regular non-symlink file, enforces a 16 MiB limit, and recomputes both values. Exactly one graph component must match both selected values without a field conflict.

gosec reports `main.go` because its SARIF location is relative to the scan root. The command therefore also receives `--sarif-artifact-uri main.go`. This makes the differing roots explicit. It does not change graph identity or permit basename/suffix search; a different result URI is skipped, while an unsafe mapping is rejected.

## Positive control

The executable test performs the complete chain:

1. builds the product CLI and official MCP Go SDK fixture;
2. scans the real vulnerable server implementation with gosec 2.28.0 rule `G204`;
3. validates the scanner output against the checksum-pinned official SARIF schema;
4. starts the real OTLP receiver and MCP stdio client/server, obtaining the runtime component plus artifact identity;
5. imports the SARIF report, grouping two `G204` occurrences into one `finding` node with observation count two and one `affected_by` edge;
6. rejects the graph through [`examples/policy-sarif-error.json`](../../examples/policy-sarif-error.json) with exit status 3;
7. exports one CycloneDX vulnerability affecting the MCP component and validates the full document against the checksum-pinned official CycloneDX 1.7 schema.

The finding evidence source is `sarif:gosec@2.28.0`, its assertion is `scanner-reported`, and its evidence level is `observed`. This records that the scanner execution reported the rule; it does not upgrade the result to `verified` or establish exploitability.

## Negative and privacy controls

- Replacing the graph's selected SHA-256 with another valid digest makes import fail before an output file is written.
- Removing the artifact URI proves that an MCP display name or digest alone cannot attach the result.
- Unit controls reject conflicting target digests, absolute/parent-traversing or unclean scanner URIs, unresolved `uriBaseId`, unsupported SARIF versions, trailing JSON, failed scanner invocations, invalid result kinds/levels/suppression states, and inconsistent rule IDs/indexes. Accepted suppressions are skipped; under-review and rejected suppression requests remain visible.
- A valid result for another exact artifact URI is skipped rather than heuristically remapped.
- Unit SARIF messages and source snippets carry explicit leak markers; the real gosec report carries its normal diagnostic message. None appears in the graph, policy report, or CycloneDX output.
- Finding nodes are excluded from CycloneDX `components` and exported through `vulnerabilities[].affects`, avoiding the claim that a scanner rule is software.

## Bounds and limitations

The core accepts at most 16 MiB of SARIF, 32 runs, 20,000 rules and 10,000 results per run, 32 locations per result, and bounded scanner/rule/path strings. It parses only fields needed for safe binding and metadata extraction. The live test uses the complete official schema as a separate interoperability gate because duplicating every extensible SARIF field in the product would add no evidence value.

v0.11 proves one scanner and one Go source file. It does not identify a multi-file package, built executable, container, Skill archive, dependency tree, or deployment image. It does not authenticate the scanner or report, execute an exploit, determine reachability, suppress false positives, retain remediation text, or scan automatically. An operator who controls both graph attributes and `--sarif-artifact-uri` can still make a false assertion; exact matching removes accidental heuristics, not the operator trust boundary.

## Validation

Local validation on Go 1.26.6 for darwin/arm64 includes:

- `go test -race ./...`, `go vet ./...`, build, `git diff --check`, and `govulncheck@v1.6.0` with `No vulnerabilities found`;
- focused importer, CLI, normalizer, policy, and CycloneDX tests;
- repeated complete `scripts/live/verify_sarif_bridge.sh` executions with real gosec and MCP/OTLP processes;
- wrong-digest, name-only, policy-exit, message/snippet privacy, OASIS SARIF schema, and CycloneDX schema controls.
- official MCP Go SDK runtime/capability drift and Dify 1.16.1 isolated instrumentation execution.

The Microsoft Agent Framework local check did not reach product execution on its first attempt because downloading `pydantic==2.13.5` exceeded uv's 30-second network timeout. A retry with a 120-second timeout remained stalled in the same 1.8 MiB dependency download and was stopped after more than four minutes without a compatibility result. The full Dify stack remains unavailable locally because Docker is unavailable. Both are required remote gates and will be recorded after the implementation commit is pushed. No v0.11 tag or GitHub release has been created.

## Direction result

The v0.10 next-step test passes, but only at single-file scope. External findings can enrich runtime evidence without turning the project into a scanner and without using framework names or source text for correlation. This is a meaningful differentiator: existing scanners answer “what did static analysis report,” while AI Evidence BOM answers “which actually observed Agent/MCP component was built from the exact scanned artifact, what did the scanner report, and should deployment policy stop it?”

The next smallest falsifiable test is a deterministic multi-file artifact manifest/root digest. The same MCP server should bind SARIF results from two files independently of absolute checkout path, file enumeration order, and scanner scan-root spelling. Until that passes, documentation must not claim package-level MCP or Skill coverage.
