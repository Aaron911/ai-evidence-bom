# v0.10.0 live source-authentication record

Status: unreleased product/schema candidate, locally validated on 2026-08-27. This record does not claim that a tag or release exists.

## Question

Can one protected live-receiver source be bound to a source-specific credential outside the OTLP payload, so a producer cannot obtain its authority by forging `service.name`, while credential rotation keeps a stable graph identity and no credential reaches evidence output or pending state?

## Standards boundary

The reviewed [OpenTelemetry Specification v1.60.0 OTLP exporter configuration](https://github.com/open-telemetry/opentelemetry-specification/blob/v1.60.0/specification/protocol/exporter.md#configuration-options) is stable and defines configurable headers for both gRPC and HTTP exporters, including the common and trace-specific `OTEL_EXPORTER_OTLP_*HEADERS` environment variables. v0.10 therefore carries a normal `Authorization: Bearer ...` value through the standard exporter header mechanism; it does not add fields to OTLP, depend on a framework, or claim that OpenTelemetry standardizes this project's authorization policy.

## Versioned binding contract

[`examples/source-auth-policy.json`](../../examples/source-auth-policy.json) demonstrates the strict policy format:

```json
{
  "version": "0.1.0",
  "bindings": [
    {
      "source": "fixture-signature-verifier",
      "tokenSha256": "d63ca837e58a59ee1817ee24e43c4dab48ddd6c4ea376156ff817eed7bbd4d1a"
    }
  ]
}
```

The example digest corresponds to a deliberately public development token and must not be used in production. Operators generate random tokens containing at least 32 bytes and store only their lowercase SHA-256 digests in policy. SHA-256 is appropriate for random high-entropy bearer material, not human passwords.

Multiple unique digests may map to the same exact, case-sensitive source so old and new tokens can overlap during rotation without changing evidence identity. The global receiver token remains a separate role that can ingest and read live state. Source credentials can ingest only, and startup rejects a credential reused for both roles.

## Positive and negative controls

- A wrong HTTP source credential returns 401 `Unauthenticated`; a wrong gRPC metadata credential returns gRPC `Unauthenticated`.
- A request authenticated only by the global receiver token but self-reporting a protected `service.name` returns HTTP 403 / gRPC `PermissionDenied` before retry deduplication, pending correlation, normalization, or persistence.
- A correct source credential maps every observation in that export to its configured source, independently of the payload's `service.name`. Component metadata is still normalized normally; only evidence authority is bound.
- A trust rule above `observed` is rejected at receiver startup unless the same exact source has an authentication binding.
- Source credentials do not authorize evidence, BOM, or stats reads when those endpoints are protected by the global credential.
- Two rotation credentials authenticate to the same source. Duplicate digests are rejected, including attempts to assign one token to two sources.
- Policy parsing rejects missing or unsupported versions, unknown fields, empty bindings or sources, surrounding source whitespace, non-canonical hashes, duplicate hashes, and trailing JSON.
- Presented source credentials shorter than 32 bytes are rejected. The raw token is never stored in policy state.
- Unit controls and a real CLI HTTP check search the graph, CycloneDX BOM, pending observations, receiver log, and rejection response for credential markers; none are retained or echoed.

## Validation boundary

Source authentication proves possession of a configured static bearer credential. It does not prove that telemetry is truthful, that a model, MCP server, Skill, or tool is safe, or that a verifier performed the check it claims. OTLP observations remain unable to self-promote above `observed`; authentication is not treated as verification.

Offline `scan` inputs remain operator-controlled files and do not use the live transport policy. The built-in receiver still lacks TLS, token expiry, audience restriction, revocation services, and hardware-backed producer identity. Non-loopback use continues to require the global token and an external trusted TLS boundary.

The graph's structural fields are unchanged from v0.9, but the shared product/schema version advances to `0.10.0` to record the authenticated live-source contract. Existing canonical signature profile v2 remains sufficient because no signed graph field or ordering semantics changed.

- a real v0.10 `collect` process using both committed source policies: wrong credential 401, correct credential 200, all node evidence bound to `fixture-signature-verifier`, and no raw token in graph, BOM, or receiver log;
- Microsoft Agent Framework live OTLP capture, producing the established Agent/model/prompt/tool graph with schema `0.10.0`;

## Direction result

This test passes the v0.9 next-step criterion: authority for a protected live source no longer depends only on a producer-controlled label, rotation retains one source identity, and the mechanism uses standard OTLP headers without framework-specific code. It narrows a real integrity gap while preserving the project's role as an evidence layer.

The next bounded question is not whether AI Evidence BOM should become another vulnerability scanner. It is whether one external SARIF 2.1.0 finding can be attached deterministically to an already discovered MCP server or Skill artifact using stable identity plus digest, retain scanner/provenance evidence, and trigger policy without importing code-scanning logic or claiming the component is safe. Failure to establish that mapping without framework-specific name heuristics is a pivot signal against findings ingestion.
