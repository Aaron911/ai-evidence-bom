# v0.8.0 field-evidence precedence record

Status: unreleased schema candidate, validated on 2026-08-07. This record does not claim that a tag or release exists.

## Question

Can the graph combine contradictory model metadata without letting arrival order or a newer weak declaration overwrite stronger field evidence, while preserving enough metadata for diff, policy, and CycloneDX consumers to see the ambiguity?

## Deterministic fixture

[`examples/conflicting-model-evidence.json`](../../examples/conflicting-model-evidence.json) contains two content-free observations for one stable model alias:

| Source | Time | Level | Version | SHA-256 claim | Endpoint |
|---|---|---|---|---|---|
| `fixture-signature-verifier` | 08:00 | `verified` | `weights-v1` | `verified-digest` | `verified.example` |
| `fixture-deployment-config` | 09:00 | `declared` | `weights-v2` | `declared-digest` | `declared.example` |

`verified` is simulated fixture input from a named compact adapter; the project does not claim that this file performs real model-signature verification.

Reproduce the graph and policy result:

```bash
go build -o ./bin/aiebom ./cmd/aiebom

./bin/aiebom scan \
  --input examples/conflicting-model-evidence.json \
  --graph-out work/conflict.evidence.json \
  --bom-out work/conflict.cdx.json

./bin/aiebom policy \
  --input work/conflict.evidence.json \
  --policy examples/policy-field-conflicts.json \
  --output work/conflict-policy.json
```

The policy command is expected to exit `3`. The selected top-level fields remain `weights-v1`, `verified-digest`, and `verified.example`; each `fieldEvidence` entry contains both candidates and sets `conflict=true`.

## Positive controls

- Normalization with verified-first and declared-first observation permutations produces deeply equal nodes.
- Continuous merge with the same snapshots in both orders produces deeply equal nodes.
- Selection uses evidence level before `lastSeen`, so the newer declared values do not replace verified values.
- Graph diff reports `fieldEvidence` changes even when the selected strongest value stays fixed.
- `forbidFieldConflicts` emits a policy violation for competing candidates.
- CycloneDX contains `aibom:field-evidence:*` candidate/selection properties and `aibom:field-conflict` markers.
- Canonical envelope v0.3/profile v2 normalizes field-candidate ordering and timestamp offsets; legacy v0.2/profile-v1 envelopes remain verifiable but cannot be used to label v0.8 field evidence with old semantics.
- Canonical input rejects inconsistent `selectedValue`, `conflict`, top-level fields, duplicate field keys, and duplicate candidate values, preventing a visibly tampered derived value from verifying after silent normalization.

## Negative and migration controls

- An observed OTLP event with `gen_ai.model.signature.verified=true` remains `observed`; telemetry cannot certify itself.
- A legacy graph that has a verified node summary but no field provenance migrates its selected mutable fields as `inferred` candidates with one compatibility observation. It does not invent field verification.
- Prompts, responses, credentials, model inputs/outputs, tool arguments, and tool results are not used by the fixture or retained by conflict tracking.

## Validation boundary

The graph schema is `0.8.0`, but no release tag is created by this iteration. The selected value means strongest-supported candidate, not necessarily current deployment state. Operators that cannot tolerate ambiguity should enable `forbidFieldConflicts`.

The candidate set retains only allowlisted metadata but is not yet cardinality-bounded. Compact `verified` observations also depend on a separately trusted adapter until source trust caps and built-in OpenSSF Model Signing verification exist.
